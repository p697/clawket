# Clawket Mobile Design System

This is the durable implementation guide for Clawket 3.0 mobile UI. Product decisions and exact recipes live in `docs/3.0/05-visual-system.md`; this document records how those decisions map to the Mobile workspace.

### Channels tab — 2026-09-19

The Channels tab keeps the settings-row language: one grouped card with the `Direct messages` row (wide tail value, chevron) above the borderless channel list (name + state value + chevron). The scope picker is a dynamic-height `Sheet` with a `secondary` `inkSecondary` hint sentence and a `SettingsGroup` of four rows (title + one-line description, accent `Check` on the current scope) — the description line is the same decision-moment exception as `ChoiceRow`. Restart-causing writes confirm through `ConfirmationModal` over the open sheet (as the Models detail sheet does); switches never simulate the pending value.

Roster recovery: the banner retry is independent of native pull-to-refresh. Keep cached rows and header spacing stable while retrying; only a real pull gesture owns the native refresh indicator. Position that indicator below the content-owned header and disable automatic inset adjustment on the roster list.

Chat earlier-history paging uses one stable 44-point header slot with a shared text `Button`: load earlier, busy spinner, or a quiet failure caption with Retry. Busy feedback starts with the request, including a single scoped pull queued behind a head refresh; it never replaces messages with a skeleton card. A fresh user drag permits one automatic top-threshold page; mounting or a page/offset layout cannot load the next page. Automatic reads and taps spin in that control. Only an actual pull owns the native `RefreshControl` (below the floating header), because starting it programmatically changes the iOS content offset. Coalesce pulls while pending and release the paging lock as soon as the read settles. Preserve a surviving content row at its screen position, skipping conditional date separators that disappear when an earlier page joins the same minute. The anchor follows new reader movement during the read, then refines committed heights and header changes. Native offsets, rather than header-adjusted manager offsets, determine whether a correction has reached the view; row bounds locate the current reading row when viewability lags. An old native page’s scroll/end-drag cannot pick the new page head after JS prepends: the same gesture retains its row and displacement until native geometry catches up, while a fresh drag takes over using its own native coordinate space. Old-child gestures retain their displacement; a grown child’s initial uncorrected offset cannot choose the new page head before acknowledgement. Native sizing completes a pending retry even when onScroll reported that size first. Native content/viewport changes retry a correction clipped to the old native content size; clipped acknowledgements never become reader movement or a return-to-bottom intent, and a fresh gesture retains priority. Explicit compensation owns that list instance alone (FlashList MVCP stays disabled); returning to the end releases the reading anchor and restores bottom following. The native beginning and existing Pro preview retain their history semantics; neither offers a false pull-to-refresh.

On Android, keep the native `RefreshControl` wrapper mounted for the conversation and disable it when no earlier page is available, without a refresh callback. Exhausting or restoring the cursor must retain the native scroll host, its reading offset and UI-thread listener binding. The visible history control still disappears when pagination ends; iOS retains its existing refresh structure.

Ordinary reading also captures a content anchor on its first native drag. If placement is unavailable, the first usable native scroll event in that gesture captures it. This requires no history page. After an acknowledged prepend, a fresh drag owns its actual finite native height even when estimate corrections left the total equal to the retired page. Retire that conflicting height evidence before row capture, so unavailable begin-layout still permits the next usable event; retain pending old-child displacement and unacknowledged offset commands. Bottom settlement releases the anchor and resumes following; a finger still scrolling owns movement during tail growth. A scoped captured anchor is the condition for disabling SDK compensation, rather than a global list setting.

Bounded finite history windows prepare the public FlashList drawing range before issuing their offset correction; fresh gestures can cancel that preparation. Native sizing determines whether the target is reachable, while layout commit alone does not establish painting. Keep the existing timeline visible and preserve the row identity; use neither a timed wait nor a covering loader. Preparation limits and explicit platform-baseline restoration are defined in `../AGENTS.md`; larger windows retain their anchor and need separate blank-window acceptance.

## 2. Visual character

Acceptance workflow (owner update, 2026-09-11): the owner performs visual acceptance on a physical device. Simulator interaction, connection and screenshot review are opt-in only when the owner explicitly requests them; older simulator-first recipes in this document are conditional on that request. Automated tests, design-system checks and code/log investigation continue normally. Preserve the owner's active pairing during QA. Development-server Fast Refresh can deliver compatible JS changes; native changes and standalone builds require their appropriate build/update flow.

Clawket 3.0 is a quiet, content-first interface:

1. Content reaches the transparent status bar; there is no bottom tab bar or system navigation header.
2. Navigation uses plain icons; quiet standalone controls and monochrome main actions carry the approved hierarchy.
3. Lists have no cards, outlines, or separators. Spacing and two levels of text provide hierarchy.
4. Color belongs to Agent identity and conversation personalization. Global controls, selection, and navigation remain neutral across saved chat colors.
5. Status is carried by avatar treatment, an icon, or a small dot—not a decorative text label.
6. Only `400` and `600` weights are valid.

Do not introduce Liquid Glass, SF Symbols, native tab bars, Material ripples, blur navigation chrome, emoji interface icons, typing-dot animations, colored status text, or gradients outside the paywall hero.

## 3. Semantic color model

New UI uses the canonical values on `theme.colors`:

| Layer | Tokens | Purpose |
|---|---|---|
| Canvas | `canvas`, `canvasGrouped` | Content pages; grouped settings pages |
| Surfaces | `surface`, `surfaceFloating` | Assistant bubbles and pressed rows; floating chrome |
| Text | `ink`, `inkSecondary`, `inkTertiary` | Primary, supporting, and time/placeholder text |
| Allowed line | `line` | Hairlines inside a settings group and dark floating-surface edges only |
| Contextual accent | `accent`, `accentSoft` | Neutral in the interface; saved color in the conversation palette |
| Foreground / overlay | `onAccent`, `scrim` | Content on accent fills; the shared 40% modal backdrop |
| Feedback | `good`, `goodSoft`, `warn`, `warnSoft`, `bad`, `badSoft` | Status rings, badges, and failure surfaces; pair color with an icon or text |
| Agent identity | `agentPalette` | Stable Agent avatar color selected by Agent id hash |

Rules:

1. Use `useAppTheme()`; ordinary UI must not hardcode hex, rgb, or rgba values.
2. Add a missing semantic value to both schemes before using it.
3. Prefer purpose names over hue names and avoid `theme.scheme` branches when a token expresses the state.
4. `PresentationColor` is only for media overlays, exported artifacts, and data visualization.
5. Pre-3.0 aliases such as `background`, `text`, `primary`, `surfaceMuted`, and `info` are removed. The design-system gate rejects their definitions and use in production or test sources.

## 4. Structural tokens

Spacing uses `Space` on a four-point grid: 4, 8, 12, 16, 24, and 32. Do not derive intermediate values with arithmetic.

Typography uses matching `FontSize` and `LineHeight` entries:

| Step | Size / line | Use |
|---|---|---|
| `display` | 28 / 34 (Android 38) | One onboarding or paywall hero title; Android's CJK fallback metrics clip Latin descenders at 34 |
| `title` | 20 / 26 | Settings or sheet title |
| `body` | 17 / 24 | Message body, row title, input, button |
| `secondary` | 15 / 20 | Preview, trailing value, system event |
| `caption` | 13 / 18 | Time, legal copy, numeric badge |

`FontWeight` exposes only `regular` 400 and `semibold` 600. A page's default UI uses two visible type steps; a third is allowed only for a page title, expanded detail, onboarding, or paywall. User content is excluded from that count.

`Radius` contains named 3.0 shapes: bubble 20, card 16, settings group 14, the four avatar sizes, sheet radii, and `full` for controls. `BorderWidth` may be used only for documented status rings, dark raised-surface hairlines, settings-group separators, and presentation framing—not list-row cards.

`ControlSize` owns the 40-point pill, 44-point floating button, 52-point settings row, and the 88-point two-line row minimum (described choice rows, skill and cron rows, the Pro card). The roster Agent row itself is `ROSTER_ROW_MIN_HEIGHT` (84: four points under that minimum, 14 above and below the 56-point avatar; owner decision 2026-09-27 after trying 80). `HitSize` provides accessible touch targets. Icons use `IconSize` or the component-owned recipe. `StatusSize` owns the 6-point list status dot and 12-point attention marker.

`Shadow` is an implementation ingredient for shared primitives. Business screens never spread it directly. `createThemedShadowStyle()` owns light-mode lift and the dark-mode hairline. Transitional primitives may still call `createSurfaceStyle()` until their old callers are removed; new 3.0 UI chooses a canonical primitive instead of assembling a surface locally.

## 5. Navigation and page ownership

The App has one native stack whose system header is always hidden. Root routes are Roster, Thread, Agent Settings, Account Settings, Search, and Paywall, with detail routes layered above them. Bottom tabs, tab-height insets, and system back buttons are forbidden.

Every page owns a symmetric header contract:

- left: one 44-point `FloatingButton` or an empty 44-point slot;
- center: a title or `HeaderPill`; while the connection is recovering, offline or failed, the title yields this slot to `ConnectionStatusPill` (Roster's spare header width hosts it trailing against Search, Thread's `HeaderPill` subtitle already carries the state);
- right: one 44-point `FloatingButton` or an empty 44-point slot.

Content begins below the safe area plus floating header. Full-screen pages use the same safe-area treatment on iOS and Android and reserve 16 points above Android's gesture area.

Backend identity and transport identity never select a visual route directly. Route availability and controls come from capability metadata.

### Waiting never moves the layout — September 29

Owner report: the Codex model and permission sheets opened with a `Loading…` line that went away when the read finished, so the sheet changed height and jumped on every open. The rule, applied across sheets and pages:

- A refresh of content already on screen keeps it visible and usable: no inserted loading line, no dimmed rows, no skeleton swap. Skeletons (`ListSkeleton`) stand in only until the first answer for that scope, and empty copy appears only after it; a later refresh keeps the last list, empty line or failure notice until its own answer replaces them.
- In an open sheet a background wait spins in the free header corner through `SheetHeaderSpinner`; it never displaces an existing header action (the composer model picker keeps Manage and refreshes silently). A write spins in the control that asked: `RuntimeSettingsSheet` swaps the tapped row's radio for the spinner until the computer confirms, and a write started elsewhere spins in the header.
- Rows whose content can resolve into an action keep that height reserved: the Codex permission summary is a 52-point row, so the 44-point Retry that an unknown result adds never changes the sheet height. While the first permission read is pending the summary reads only `Applies to this conversation.`, never `Unknown` with a disabled Retry.
- One wait keeps one loader: a `LoadingState` whose stage label changes (export: Connecting → Loading history) stays the same instance, so its scene and grace period do not restart.
- A sheet that closes animates away with the content it showed; it never unmounts mid-frame or swaps to empty copy on the way out (`CommandOptionPickerModal`).
- Typing in Search refines what is on screen; placeholders appear only until the first message search answers after the field was last empty. Channels & Devices refreshes a tab it has already shown in place (tab switch, pairing decision, reconnect), and the Cron editor keeps `No runs yet` in place while the history re-reads.
- A failure notice stays in place while the next attempt runs and changes only with its outcome; the pressed control spins meanwhile (Connection page Reconnect, Onboarding Connect, the Cron list and OpenClaw management Retry). The Roster's unavailable card likewise holds its place, with its Reconnect spinning, until a pressed retry answers, so the rows under it never jump. An action drawn on a held notice never starts a second attempt.
- Revisited pages start from the last answer of the same live adapter and refresh in place: the Agent profile summary (hero heartbeat line and stat values) and the Cron Runs tab's first page. A replaced adapter starts over.
- OpenClaw management keeps a section's content while it re-reads after Save, Attempt Fix, Retry or Run diagnostics again; the Companion covers only a section with nothing to show yet. Edit waits for the re-read that returns the config hash, and a diagnostics re-run spins its own button.
- During the foreground recovery window Tools, Channels & Devices, Logs, OpenClaw management and Model health keep what they show and insert no offline notice; the header already says `Reconnecting…`. Their in-place offline copy remains for a sustained outage.

### Onboarding connecting stage — September 30

## 9. Verification and style ratchet

For every UI batch run affected render tests in both light and dark schemes, `npm run typecheck`, and `npm run check:design-system`. Tests assert capability degradation, all five page states, no row border, and the set of rendered font sizes; screenshots are reserved for human device acceptance.

`scripts/check-ui-style.mjs` scans every production and test TypeScript source and rejects any member outside the exact canonical `Space`, `FontSize`, `LineHeight`, `FontWeight`, `Radius`, and `ControlSize` sets. It also rejects removed motion and semantic-color aliases and malformed source input, alongside hardcoded colors, numeric radii/fonts/borders, `FontSize` arithmetic, outlined list rows, emoji icon literals, more than three `FontSize.*` references per screen, React Native `KeyboardAvoidingView`, raw `Shadow.*`, unapproved native `TextInput`/`Switch`, and bottom-tab dependencies. Existing debt is stored per file and rule in `scripts/ui-style-baseline.json`; counts only decrease. Never update the baseline to hide a regression.

The docs checker verifies canonical and transitional exports, all 18 canonical `theme.colors`, the `BorderWidth`, `ControlSize`, `FontSize`, `LineHeight`, `PresentationColor`, `Radius`, `Shadow`, `Space`, and `StatusSize` families, plus `createSurfaceStyle`. Removed color aliases must stay absent from `theme.ts`; remove transitional component names from this document and its checker only in the same change that deletes the last real caller.

### Keyboard reveal on iOS (2026-09-11)

Chat retains React Native padding `KeyboardAvoidingView` on iOS after a model-sheet return reproduced correct animated height with unapplied native padding. On Android, RN's end-event-only layout corrected a stuck Send/Back gap but visibly lagged the keyboard animation, so the chat-specific `AndroidChatKeyboardAvoider` follows native frame progress on the UI thread. Its stable plain host filters incoming animated/GC padding and owns the final React baseline; that baseline stays unchanged during motion, with one fenced update at the end. Start events report a destination, not the current height. Seed an open keyboard and recover missed starts from actual frame height/progress, preserving offset and input/list identities. The style gate permits only this exact iOS-native/Android-scoped branch in ThreadView. Verify animation during real sends, rapid reversal, sheet return and focused navigation on devices. Unit tests of the handoff do not prove Fabric frame timing; do not substitute reset timers, remount keys or global native flags.

On iPhone, screens that must keep one region just above the keyboard (Onboarding pairing code + Connect) use keyboard-controller's padding `KeyboardAvoidingView` to shrink the viewport plus `useKeyboardRevealScroll` (`src/components/ui/`) on a `Reanimated.ScrollView`. The hook measures the anchored region once (layout/focus), re-derives its on-screen position from the live scroll offset on every keyboard transition, and scrolls only the remaining shortfall in step with the keyboard's real height progress. Do not use RN `automaticallyAdjustKeyboardInsets` (a third-party keyboard's transient frame over-scrolls by the full keyboard height) or the library `KeyboardAwareScrollView` (its cached input position is not refreshed after scrolling, so a keyboard resize re-adds the whole distance and bounces back). Number-pad inputs omit `returnKeyType` so React Native does not attach an accessory toolbar that changes the keyboard frame again; the visible primary button is the submit path. Android keeps adjustResize. On iPad, pairing uses the full ASCII keyboard with Go (the backend-specific code validator is unchanged) and native `automaticallyAdjustKeyboardInsets` and `on-drag` dismissal, with controller avoidance/reveal disabled so only one owner moves the form. Keep the field and Connect action scrollable. The app provider disables hidden-field keyboard preloading on iPad; first focus belongs to the visible input. Verify cold launch and return from another app on physical iPad (2026-09-20 keyboard investigation).

### Triage for "placeholder / text sits low" reports (2026-09-11)

A single device screenshot is not evidence of a layout defect. A form text field was reported with a low Chinese placeholder on a phone; the same build on a clean simulator install measured 18.67 / 18.33 points above / below the glyphs inside the 52-point field (centered), in light and dark, and a plain UIKit probe with the identical configuration (system 15, inset `textRectForBounds`, `defaultTextAttributes`, CJK and Latin `attributedPlaceholder`, RN prop order) centered every variant. The phone rendered correctly after a reinstall. Before changing `FormTextInput`, `CompositionSafeTextInput`, or any input typography:

1. Reproduce on a clean build, not a Fast Refresh / hot-reloaded session or a stale install; a stale `UITextField` placeholder frame disappears on the next full layout and is not a code bug.
2. Pixel-measure a simulator screenshot (`xcrun simctl io booted screenshot` and count field rows against glyph rows) rather than judging by eye; report the field height and the above/below space.
3. Compare typed text, placeholder, and caret in the same field; if only one of them is off, isolate whether UIKit or RN differs with a minimal UIKit probe before adding optical offsets.
4. If it only reproduces on one OS version (device fleet includes iOS 26.0–27.0 betas), record the version; do not add a hack for a beta-only rendering change.

The chat composer and user bubble report of 2026-10-01 was a real offset, measured with 17-point text on 24-point lines. A clean Release simulator build (iOS 27) put the composer placeholder and typed text 1.8–2.0 points low with the caret centered, because React Native gives `TextInput` none of the baseline offset its `Text` gets and UIKit draws the whole surplus above the glyphs. On the SM-A566B (Android 16), bubble lines containing CJK sat 1.3–1.5 points low, from fallback line spacing, while Latin lines were centered. Under the zh-Hans system locale the editor sat 1.0–1.7 points low for every script; under en-US, typed Latin was centered. iOS bubble text measured within 0.5 points. After the lifts in `src/chat/textCentering.ts` every case measured within 0.33 points. The caret moves with the text and now sits up to 1.8 points above the capsule center.

On Android under a Latin locale the empty editor's placeholder measured 2.00 points high and its 19-point caret 1.83 points high, against −0.33 points for typed Latin and a centered 22.7-point caret. React Native's `CustomLineHeightSpan` reaches only typed text: `TextView` lays out the hint without it, and Android 16's `Editor` draws an empty editor's caret on the text layout's empty line, which `StaticLayout` builds from the paint's metrics alone. Both are a bare Roboto line (ascent 0.93 em, descent 0.24 em) at the top of the 24-point slot. Under a placeholder Roboto sets, the composer turns on `includeFontPadding`, the native `EditText` default: it lowers those two lines to Roboto's top (1.06 em), while the span pins every typed line to its own ascent and descent, so typed text keeps its layout and nothing changes on a keystroke. A pixel model of that layout code (Roboto's metrics, `getFontMetricsInt` rounding, 420–480 dpi) reproduces the measures above within 0.4 points and puts the placeholder within 0.3 points of center and the empty caret within 0.7 points (0.8 at 1.3× text), its top edge level with the typed caret's. Not yet measured on the device: the phone was in use when this landed (owner instruction, 2026-10-01). CJK placeholders keep the measured lift above; Thai, Devanagari and Arabic ones come from other fonts, are not measured and keep their layout.
