# Clawket 3.1：Agent 接入与 Agent Home 市场研究

研究日期：2026-09-23。讨论稿，不是实施规格，不修改 3.0 决策。发布状态按负责人提供：3.0 已发布，App Store 已通过，Google Play 审核中。

## 研究口径

- 主观察窗口为 2026 年 6–9 月；使用当日官方文档、商店、仓库快照。更早的版本记录只用来确认竞品已经具备某项能力，不用来证明近期增长。
- App Store 数值统一为美国区；价格为页面公开 SKU，不保证每个用户都会看到全部 offering。评分数不是下载数，GitHub stars 不是活跃用户，npm 下载也不能直接当用户。
- 最近问题来自公开 issue 和评论，是用户报告，未在本次研究中复现，不代表全体用户体验或已确认缺陷。商店公开评论通常不是完整时间序列。
- 本次没有安装并实测竞品，没有取得竞争对手后台、收入账单、留存或全球下载数据。不能据此计算 TAM 或断言某 Agent 的实际使用量排名。
- 核心判断：需求存在，官方入口正在压缩单厂商遥控器的空间；跨厂商、沿用用户原有环境、可靠接续与优秀的移动交互值得验证。

## 2. 接入候选：优先级与边界

### Codex：第一优先级，卖点是用户原来的 Codex

官方 App Server 面向自定义客户端，提供会话历史、审批和事件流，适合研究深度接入；官方配置支持自定义 provider。建议首先验证 Bridge 本地通过 stdio 驱动 App Server，再复用 Clawket 的连接体验。文档对 app-server 命令及 WebSocket 路径存在实验性/生产支持提示，不能称为稳定不变的公共远程协议。[App Server](https://learn.chatgpt.com/docs/app-server)、[模型提供方配置](https://learn.chatgpt.com/docs/config-file/config-advanced)。

明确可见的官方 Remote 前提是 ChatGPT 账户、workspace、Codex access，以及设备间身份匹配；不应把它简化成“所有没有付费订阅的人都不能用”。用户原有第三方 provider 是否能在官方 Remote 完整使用，需要独立实测。[Remote 设置](https://learn.chatgpt.com/docs/remote-connections)。

最有力的近期需求线索是 Happy 用户 9 月 20 日报告：远程会话没有沿用其 Codex 配置里的第三方 provider。另一个 9 月 3 日问题涉及工具格式与模型网关不兼容。二者说明“支持 Codex”与“忠实保留用户自己的 Codex 环境”之间有距离，但不证明这些问题普遍发生。[配置反馈](https://github.com/slopus/happy/issues/1818)、[网关反馈](https://github.com/slopus/happy/issues/1746)。

接入验证重点：真实 provider/model、项目路径、已有会话恢复、运行中接续、工具审批、长回复和图片、重复发送防护。历史可读、会话可恢复、正在运行的桌面会话可同时控制，是三种不同承诺。Remodex 自述部分桌面实时同步使用私有 IPC，这类能力不宜直接变成 Clawket 首版承诺。[Remodex 技术说明](https://github.com/Emanuele-web04/remodex)。

### Claude Code：高优先级，API 与企业网关用户有明确空缺

官方 Remote Control 的 requirements 明确排除 API Key、自定义 `ANTHROPIC_BASE_URL`、部分云平台配置。这是比“官方没有手机版”更可靠的切入口。[官方 Remote Control](https://code.claude.com/docs/en/remote-control)。

Agent SDK 提供流式、会话、审批和 hooks，但它与“接管用户正在运行的 Claude Code CLI”不是同一个集成目标。SDK 文档明确限制第三方提供 claude.ai 登录/订阅额度，也有相应品牌规则。优先研究用户本机已有 CLI 的连接，以及有明确支持的 API 认证路径；不能因能运行 SDK 就声称可复用所有订阅、热接管所有会话。[Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview)。

Claude Code 支持组织现有网关，但官方不支持通过网关使用非 Claude 模型。应把“Claude 经 API/企业网关运行”和“任意模型替换 Claude”分开描述，后者不能成为正式兼容承诺。[网关文档](https://code.claude.com/docs/en/llm-gateway)。

### Pi：适合成为第三个候选，有原生界面机会

上游原地址 `badlogic/pi-mono` 当前重定向到 `earendil-works/pi`；当日累计约 108.6k stars，9 月 22 日有发布，说明生态值得认真关注，但不是用户数。Pi 有原生 RPC 与 TypeScript SDK，适合独立客户端。[仓库](https://github.com/earendil-works/pi)、[发布记录](https://github.com/earendil-works/pi/releases)。

RPC 提供 prompt、steer、abort、会话操作及扩展 UI 交互。集成难点包括扩展对话框、工具表现、会话分支，以及区分一轮 agent_end 与真正停止自动工作的 agent_settled。建议以 RPC 做短验证，保留用户 extensions 和 provider；不默认把 Pi 等同于 ACP，也不为了统一 UI 虚构 Pi 没有的审批能力。[RPC](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md)。

### OpenCode：值得接，技术形态很合适

OpenCode 有 headless HTTP server、OpenAPI 与事件接口，原生支持客户端/服务端拆分；provider 配置覆盖自定义端点。累计约 209.5k stars 是生态关注度线索。[Server](https://opencode.ai/docs/server/)、[Providers](https://opencode.ai/docs/providers/)、[仓库](https://github.com/anomalyco/opencode)。

它适合作为 Pi 之外的另一个第三名候选。选择顺序应由 Clawket 现有用户重叠、首周使用与验证成本决定。注意当前站点同时存在不同版本的文档，实施前要冻结支持版本；不能拼接 v1/v2 API。ACP 可作为未来增加后端的公共通路，但能力协商、历史恢复和权限仍需逐后端验证。

### Grok：必须拆成三项

| 对象 | 当前证据 | 建议 |
|---|---|---|
| Grok 模型 API | 可供应用调用模型 | 不等于接入用户已有 Bot；模型可由现有 Agent 的 provider 承载 |
| Grok Build | 官方支持 headless 与 ACP；`grok agent stdio` 为集成入口 | 加入技术观察名单，优先级低于上述四个 |
| Grok Bot | 有持久 Bot、云电脑、文件、例行任务和独立移动端 | 本次未找到接管用户既有 Bot 会话的公开 API/协议；不承诺 3.1 接入 |

来源：[Grok Build](https://docs.x.ai/build/overview)、[CLI](https://docs.x.ai/build/cli/reference)、[Grok Bot](https://docs.x.ai/grok-bot/overview)、[API 参考](https://docs.x.ai/developers/rest-api-reference/inference)。

Grok Bot 实际上属于生产力方向，官方列举了业务和办公任务；把它只当社交聊天工具会低估它对 Agent Home 的产品启发。支持 MCP 工具、接入其他应用，属于它调用外部工具的方向，不能据此推出 Clawket 能控制它。[Bot 使用文档](https://docs.x.ai/grok-bot/get-started)、[Connectors](https://docs.x.ai/grok/connectors)。

8 月 26 日官方文章已经介绍多个 Bot 在群聊中传递工作。因此 3.5 的“Agent 群聊”并不是空白赛道；Clawket 值得探索的是跨厂商、跨用户自有运行环境的交接，以及可理解的责任和上下文边界。[Grok Bot 多 Bot 工作流](https://x.ai/news/grok-bot-more-plans)。

### Muse：体验参照，暂不排接入

9 月发布的 Muse 有专属 VM、长期记忆、后台任务和关键行为确认，独立 App 与 WhatsApp 是公开入口。本次未发现可由第三方列出、恢复、继续用户既有 Muse 会话的接口。模型可调用、聊天入口存在、完整 Agent 能接入，是三个不同判断。[Meta 发布说明](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)。

## 4. Agent Home 应该占据什么位置

建议产品定义：**让你常用的 Agent 住在一起，随时接着做事。** OpenClaw 继续是管理深度最强的核心，新后端贡献新的任务场景。

用户看到的首先是“我的研究助手”“Clawket 开发项目”“家里的管家”，后端品牌是身份信息。可以共用名字、头像、未读、输入框和结果阅读，但必须尊重对象差异：OpenClaw 有持续人格和主会话；编码 Agent 的会话通常绑定项目、工作目录或 worktree。进入 Codex/Claude 时应恢复合适的项目/任务，而不是强行制造一条永久 main。

建议把一致性落在四个用户动作：发起、跟进、决定、查看结果。管理页面按实际能力出现；Cron、skills、模型配置和文件权限不需要为了整齐而做到虚假一致。

值得验证的三个体验假设：

1. **一次连接自己的电脑，发现已安装 Agent。** 沿用现有模型、skills、项目和权限配置。选择后端时不要求重新建立一套模型账户。产品上减少重复配对，协议上仍保持 host、backend、transport 的身份边界。
2. **“需要我”比“工作中”更有价值。** 审批、补充信息、失败恢复和完成结果应有可信的状态；离线明确显示更新时间。未来通知先处理需要动作的事项，再考虑普通回复，不用持续刷新动画制造在线幻觉。
3. **先做一键交接，再做群聊。** 将结果、来源和下一步要求显式交给另一个 Agent，先由人确认。用户如果持续使用这一动作，才值得投入自动协作。原始整段历史不应默认跨模型扩散。

场景例子：OpenClaw 整理一个需求，用户从手机把需求与相关文件交给 Codex；Codex 返回修改结果，用户再请另一个 Agent 评审。这是 3.2–3.5 的设计探索，不是当前能力。

“有品位”需要可验收的表现：长聊天不卡、返回后位置不丢、草稿不丢、审批不误触、图片/文件能查看、工具过程可折叠、恢复时不会重复执行。Clack 的语音定位提示了离桌使用的机会，但其规模太小，还不足以证明语音应成为首页主导航。

## 5. 建议版本节奏

| 阶段 | 建议范围 | 成功条件 |
|---|---|---|
| 3.1 接入 | Codex 第一、Claude Code 第二；Pi 为第三名实验候选，OpenCode 作替补/下一批。最多两项正式支持、一项实验支持 | 新建/继续任务、流式、停止、真实审批、历史恢复和原有 provider 配置形成闭环；OpenClaw/Hermes 无退化 |
| 3.2 打磨 | 按真实留存决定 Pi/OpenCode 转正；优先重连、长会话、结果/文件、项目组织；小范围验证“需要你”通知和人工交接 | 多 Agent 用户真的每周回访，跨设备接续不丢状态；新增价值高于支持成本 |
| 3.5 愿景 | 人发起的跨 Agent 工作房间；有明确负责人、交接输入和验收结果，再探索自动协作 | 用户已频繁手动交接；可追溯来源、权限、费用和责任；防止自动互聊循环 |

若 Claude 接入无法清楚保证认证边界或会话接续，正式名额让给 Pi/OpenCode；不要为了品牌齐全发布半个适配器。上述排序是研究建议，不是冻结的版本承诺。

3.0 规格明确没有多隧道并行、远程推送和 Relay 活动摘要；Agent Home 跨连接实时状态与通知不能作为接入新后端的隐含赠品。这部分在 3.2 需要单独核算移动后台机制、隐私与 Relay 成本。Relay 不落消息的既有承诺继续成立，不能用市场研究覆盖它。

对商业化的建议：先沿用 3.0 的价格框架，观察第二个常用 Agent 是否提高付费与留存；如现有一连接免费额度让用户根本无法体验第二后端，可讨论小规模体验实验。不要按每个后端分别卖一次，也不要把模型 token 成本混进连接器费用。均为后续讨论，不改变当前付费规则。

## 6. 用最小投入验证方向

建议在 3.0 稳定观察后进行 2–3 周设计伙伴测试。人数和阈值是规划建议，不是市场统计。

- 招募约 20–30 人，分别覆盖现有 OpenClaw 用户兼用编码 Agent、API/网关用户、Pi/OpenCode 用户；保留使用官方手机端的对照体验。
- 记录从发现 Agent、连接成功到完成第一轮任务的漏斗，失败原因按认证、网络、provider、会话/工具兼容分开。
- 北极星候选：每周在手机成功继续或推进至少一次既有 Agent 任务的用户数。发送量不是唯一成功指标。
- 重点观察第二周重复使用、新增后端与 OpenClaw 的共同使用、真实审批完成、接续成功率、每活跃用户支持成本；区分已有活跃用户自选择与新增接入产生的效果。
- 每个候选完成同一组验证：电脑启动→手机继续→审批→切网/后台→停止→恢复；另测第三方 provider 和原有 skills。只做手机新会话，不能冒充已有会话接续。
- 暂不建设群聊调度器、统一记忆库、插件市场、云端代跑或完整移动 IDE。用已有能力验证任务闭环。

3.0 旧调研记录曾显示双后端用户留存较好、多连接触发付费较多，但它是历史关联数据，可能由重度用户自选择造成，不能当作“再加一个后端必然提高留存”的因果证据。本次没有重新查询线上数据。[3.0 既有调研记录](../3.0/00-decisions.md)。

讨论优先定三件事：新用户优先服务“OpenClaw 用户的第二个 Agent”还是“独立编码 Agent 用户”；3.1 必须支持哪些已有会话接续；是否接受两项正式接入、一项实验接入的发布上限。

## 7. 后续讨论：先验证一条完整协作链

负责人提出希望探索更大的 Agent Home 方向，尤其是 OpenClaw 向用户自己的 Codex 委托工作。以下是方案探索，尚未决定实施。

补充核验发现：OpenClaw 当前官方文档已描述 Codex 原生集成、通过 ACP 运行外部编码 harness，以及子任务完成回传。没有在本次讨论中实测当前安装版本或 Clawket UI 的完整兼容性。应先评估复用这些路径，再决定是否增加独立的协作服务。[OpenClaw ACP 概览](https://docs.openclaw.ai/tools/acp-agents)、[结果投递模型](https://docs.openclaw.ai/tools/acp-agents/delivery)。

据此，另一个值得优先验证的 3.1 方案是：保持 OpenClaw 管理深度，只增加一个 Codex 接入，完成“委托→接收→独立任务→审批→返回结果→手机查看”的闭环。与前文多后端接入方案比较后再定范围；不同时承诺两套计划。

技术上不必先修改各家 harness 源码。来源 Agent 可以通过现有工具/插件/MCP 发起委托，skill 说明使用时机；本地 Bridge 执行身份与授权检查、会话映射、任务记录和结果回传。目标 Agent 通过原生接口执行；单向委托并返回结果不要求两端都拥有自由发起委托的 skill。

同机优先验证已有本地路径；跨机器时，各端 Bridge 主动连入云端，再经认证路由投递，不需要云端穿透网络直接连接电脑。任务内容与恢复记录优先持久化在用户机器；若未来要求来源和目标都离线时仍由云端接收、长期排队，就涉及新的持久化与隐私决策，不能默认塞进当前不落消息的 Relay。

真正的工作量在任务语义：确认接收不代表完成；运行结束不代表通过验收；超时不代表没执行；取消不代表撤销已有改动。目标端必须根据原始用户授予的范围判定权限，Agent 转述不能升级为用户授权。相同任务 ID 去重并恢复；原生接口无法确认的执行状态应显示待核实，不能盲目重试。

可参考 A2A 的 task/context、需要输入、完成/失败等语义，但这不意味着 Codex、Pi 等自动实现该协议，也不要求首版建设完整 A2A 平台。[A2A 任务生命周期](https://a2a-protocol.org/latest/topics/life-of-a-task/)。

验证价值应比较两种完成同一任务的方式：直接找 Codex，与从已有 OpenClaw 上下文委托 Codex。若委托只增加解释、等待和费用，应继续把资源放在连接体验；若它稳定省去搬运需求、文件、状态和结果的工作，再扩展第二种目标 Agent 和跨机器场景。
