# Composer upgrade — 2026-09-06

The owner authorized a first complete refinement of composer quality, long-form editing, unified actions, and keyboard behavior. This supersedes the original fixed composer recipe without changing backend scope or transport contracts.

## Implementation

- One native input survives compact/full-screen transitions. Three visual lines expose expansion; compact growth stops at five lines, with scrolling beyond the cap. A bounded native Text measurement avoids the paste input's unreliable Fabric content-size notifications without replacing marked text.
- Full-screen writing has a collapse action, keyboard dismissal, the same model/thinking controls, and visible connection feedback when offline. Its temporary placeholder retains the original timeline geometry, and hidden background content is excluded from accessibility.
- Add, dictation, Send, and Stop share a 40-point visual / 44-point target / 20-point icon recipe. Primary actions have no unrelated floating shadow; empty drafts reserve a disabled Send or available dictation slot. Attachments live inside the composer, and attachment-only drafts can send.
- Existing keyboard-controller 1.20.7 owns iOS keyboard animation; no dependency upgrade. The header remains fixed. The list follows viewport changes only while already following the bottom; reading history and expanding tools must retain position. Android continues to use native adjustResize rather than adding a second keyboard offset.
- Debounced draft persistence now flushes the final edits on scope departure. Clearing a submitted draft also cancels pending saves so cleanup cannot restore stale text.
- Stable native layout hosts and post-layout focus preserve the keyboard through expansion/collapse; compact styles explicitly clear expanded flex properties. The hidden measurement has its own six-line height so it cannot inherit a one-line clipping constraint. Foreground connection recovery no longer forcibly dismisses the editing keyboard.
- iOS native-owned draft text uses the canonical light/dark ink through DynamicColorIOS. A live appearance change must recolor existing attributed text without rewriting the draft or marked text; ordinary static color props only refreshed typing attributes in the installed native input.

Reference: [Keyboard Controller](https://github.com/kirillzyusko/react-native-keyboard-controller/blob/main/docs/docs/api/components/keyboard-sticky-view/index.mdx) documents the distinction between moving an accessory and resizing a container. Implementation was checked against the installed 1.20.7 source; newer chat-scroll APIs were not assumed available. The third-line expansion behavior is the owner's explicit Telegram reference.

## A+ single-row composer — 2026-10-01

Owner decision 2026-09-30 (A+ chat design, step 3) supersedes the two-row card and the 40-point action recipe above:

- One row: a 44-point add circle, a capsule (radius `xl`, surface or glass) holding pending attachments, the draft and the model chip, and a 44-point send / voice / stop circle. Circles and capsule share the bottom line, so a growing draft rises above them. Send is the user's own bubble color; Stop stays ink; the circles use the capsule's surface or glass. Full-screen editing keeps its header and bottom toolbar, and the native input keeps one parent chain across both modes.
- The model chip shows the model's icon and short name (`shortModelLabel`; Claude ids read as the product) on a faint tint of the user's bubble color, and only the icon while a draft is written. It opens the model sheet, which now also holds thinking depth, context remaining and the project path (the runtime settings overview for Codex / Claude Code adds permissions, context and project rows). The thinking chip left the composer; the permissions shield appears in the capsule only for full access or an unknown mode.
- The Thread header's idle subtitle is Online in the accent; context remaining and the project path no longer appear there.
- Owner report 2026-10-01 (device): the add and voice circles looked grey and dirty while the header buttons and the capsule looked right. There is no blur: the glass is an 80% fill. Android draws an `elevation` shadow beneath the whole outline, and the see-through fill showed it differently per control, measured on device: the header buttons and the voice circle an even grey (brightness 242), the add circle a grey ring around a pale octagon (243 / 252), the capsule nearly clean (252). So the bottom row mixed a bright capsule with grey or blotchy circles. The glass keeps its fill and, on Android, uses `Shadow.floatingOutside` (a box shadow React Native clips to the outside on both platforms); every glass control now reads the same (251–252, even). Dark glass gained a faint `ink` rim because dark controls blended into the dark wallpaper.

## A+ motion, batch 1 — 2026-10-01

Step 4 of the A+ chat plan (owner request 2026-10-01: polish motion and feel everywhere) implements the approved motion prototype (PMotion, 2026-09-30) for the send path and live presence. Recorded on device before the change (SM-A566B, main at 2ccdecc9): the composer cleared with no motion; send → mic (about 0.7 s, while the message was still leaving) → stop, and stop → mic were hard cuts; the header status and the live pill's steps cut instantly.

- Send: the user's bubble flies in from the composer. X and Y use separate curves over 300 ms (Telegram's send transition), starting 118 points toward the leading side and 148 below, growing from 94 % size and 35 % opacity about the bubble's bottom trailing corner. This supersedes, for sent rows only, the 2026-09-16 rule that entrances move position at final size and full visibility. That rule removed scaling and fading because rows replayed on recycling and changed size between states. The protections it introduced remain: one latched entrance per render identity, the conversation-owned played ledger, metadata reserved from the first frame, and measurement cells that never claim an entrance. A reply still rises 8 points at full opacity.
- Composer slot: send, stop and mic replace one another by popping from 60 % with a fade (150 ms) through `SwapEntrance`. The control shown when the composer mounts never animates. While the local send is still leaving (`sendInFlight`), the slot already shows Stop, dimmed and inert, so it no longer flashes the mic. Stop becomes live when the run starts. The mic's touch target stays mounted while only its surface turns into send, so a held dictation keeps its press.
- Presence: the header's status sentence fades in and rises 4 points (200 ms) when it changes, and the presence ring fades in and out. A live pill's new step slides in from 6 points below (160 ms); its first step and its ticking time do not move.
- Haptics: send taps lightly. A reply that ends while its conversation is focused and the app is active plays Success. A failed run, a run error, or a new exec approval plays Warning, once per approval. Android uses `performAndroidHapticsAsync` (`Virtual_Key`, `Confirm`, `Reject`) instead of the coarse vibrator-based impact. Streaming, cancellation and background updates stay silent.
- Reduced motion: a sent bubble fades in place, a reply appears at once, slot controls and steps fade in place, and the live pill's spinner becomes a still glyph.
- Device check (SM-A566B QA build, screen recording, frame by frame): the first build drew the new bubble at its final place for one frame before the flight started. A Reanimated style is first committed with the shared value's initial value, and the reset in the layout effect lands a frame later; a recycled cell keeps the previous row's values. A row whose entrance is still to play now mounts its own animated view at the motion's first frame, and the list asks whether an entrance is pending without claiming it, so a played row never mounts hidden. The header's status sentence had the same flaw: the new words showed for about 40 ms before fading in. It now enters as its own view. After the fixes the bubble emerges from the composer and lands about 300 ms after the tap. The slot pops in to a dimmed Stop within about 125 ms, which fades to full ink in about 140 ms when the run starts. The phone's vibrator log shows `VIRTUAL_KEY` on send and `CONFIRM` when the reply ends.
- Seen on device and left for batch 2: when a multi-line draft is sent, the list shifts about 45 points for one frame while the composer shrinks. At completion the reply bubble and its clock appear about 30 ms before the text fades in. Once, the live pill's elapsed time jumped from 10 s to 20 s within 0.1 s.

Next (batches 2 and 3): smooth list follow without the 15–30 point jumps measured when the live pill appears, at the first token and at completion; the reply clock and tail appearing at completion without a layout jump; the wallpaper's small gradient step on send; the composer's first-line clip while it grows; sheet and navigation polish.

## Immediate send feedback — 2026-09-16

The owner requested responsive sending while retaining tunnel reliability. Inspection confirmed a shared OpenClaw/Hermes controller path across Relay, local, Tailscale, Cloudflare and custom transports: system network lookup → reuse health confirmed within 3 seconds or probe → attachment preparation → local bubble and prompt. The fast probe is 1.5 seconds; a failed Gateway probe reconnects and waits at least 8 seconds for readiness. This made local feedback depend on network latency. A preflight improves recovery but cannot guarantee the subsequent write succeeds or its acknowledgement arrives.

The composer now synchronously accepts the message into the existing session/connection outbox, clears only that submitted draft, scrolls and shows its pending bubble. The same health/reconnect checks and attachment processing then run. Successful preparation transfers the same bubble ID to the existing prompt/acknowledgement path; no additional polling, retries or backend protocol change is introduced. The user can write their next draft while waiting; late preparation never puts old attachments back into it. Pending means locally accepted, not delivered, and no Agent run is claimed before dispatch.

- Failed health or attachment preparation: preserve the original bubble and attachments in the held outbox; Edit, Remove and Send now remain available. Do not silently retry after a failure.
- Prompt dispatched but acknowledgement fails: preserve one uncertain bubble through existing reconciliation; never enqueue a retry or refill the composer because the backend may already have received it.
- Session/adapter change or unmount: retire the old preflight and hold its source message. Removed messages and runs discovered during reconnect are rechecked before dispatch. Duplicate taps retain the synchronous guard.
- Existing run: retain the one-prompt-per-turn queue and its ordering. Full outboxes keep the unsent composer draft.

This follows [Matrix local echo and transaction matching](https://spec.matrix.org/unstable/client-server-api/#local-echo): immediate local display and eventual delivery evidence are separate. [Firebase's local-write events](https://firebase.google.com/docs/database/web/read-and-write#work_with_data_offline) provide another example of network-independent UI feedback. We keep Clawket's conservative ambiguous-send policy rather than assuming all backends support safe automatic retries.

Scope: this changes perceived send latency, not model response time or physical network reliability. The existing 1000ms reply presentation gap remains. The outbox is in memory across navigation; durable offline delivery across an App kill is not added. Automated tests hold network/health/attachment promises unresolved to verify immediate local feedback and cover both backends plus transport descriptors, failed preparation, explicit retry, next-draft preservation, duplicate taps, scope departure, recovered active runs and ambiguous acknowledgements. Device feel and real network acceptance remain owner-performed; no simulator is required.

## Continuous message presentation — 2026-09-16

The owner's phone test confirmed faster local feedback but reported a bubble that changed size, disappeared and reappeared. Code inspection found several independent causes: queued messages omitted time/status reservation and used a separate caption plus reduced opacity; dispatch inserted metadata and a timestamp, changing line wraps and time separators; sent entrances scaled from 0.92 and faded from zero; recycled rows could replay their entrance; history and final replies could replace list keys; and the thinking indicator could disappear before the text pacer had published anything. Dispatch also requested a second scroll after preflight.

- Local sends now use their creation timestamp, final time/status reservation and full-opacity bubble immediately. Clock/pause/check/uncertain glyphs share a fixed slot. The original image preview and dimensions remain while prepared attachments go to the backend; attachment-only captions match before and after dispatch. Outbox items stay after live activity regardless of timestamp.
- `UiMessage.renderKey` separates local presentation from backend lookup IDs. Exact ID or unambiguous role/idempotency-key matches retain presentation through history reconciliation; equal text alone is not evidence. Waiting, streaming and finalized replies share a run/segment key, so the Markdown view and pacer survive finalization. Recovery preserves an existing run's presentation start time.
- Entrances animate only a short vertical offset at final size and full visibility. A conversation-owned played ledger prevents replay on cell recycling/remount, and measurement cells do not claim animations. Reduced motion stays still. Thinking switches only when paced text is visible; whole-body fades are removed and reply metadata reserves space before finalization.
- Sending requests one scroll on local acceptance. Existing health checks, reconnect behavior, one-prompt-at-a-time queue, ambiguous-send handling and backend/transport contracts remain in place.

This applies [React's state/key identity rules](https://react.dev/learn/preserving-and-resetting-state) and [FlashList's separate cell/measurement rendering](https://shopify.github.io/flash-list/docs/usage/), checked against the installed FlashList source. Automated regressions cover outgoing subtree identity and text reservations, history echo identity, attachment previews, one scroll request, waiting/stream/final Markdown identity, delayed pacer output, recycled entrances, scope changes and reduced motion. They do not measure native frame timing: the owner will test short/multiline/image sends, slow replies and reconnection on OpenClaw and Hermes on the phone. No simulator or service changes are needed for this iteration.

## Preserve tool-separated replies and sends during hydration — 2026-09-16

A subsequent phone report described one disappearing user message and a repeatable collapse of tool-separated text after completion. Client code had an explicit `replaceAssistantMessagesInCurrentTurn` policy that replaced multiple transcript messages with the locally received final text. The controller also discarded committed stream segments at completion, while its post-run history callback could clear a newer run's transient state. These are client behaviors; the protocol does not require rendering an aggregate final as one bubble.

Completed live text and tools now move into history together with the same render keys and order. Segments record how many tools preceded them, so two consecutive tools cannot be split by the following paragraph. Exact repeated prefixes in cumulative final text are removed; tail-only finals, intentional repeated text, failures and cancellations retain their content. Reconciliation stays within the matched user turn, updates known tools/text in place, preserves local boundaries through stale/split/aggregate snapshots and retains newly discovered server content. Transcript text is flushed before embedded tool calls so cold history also respects that boundary. No Gateway, Hermes, Relay or transport changes are required.

The disappearing message could not be attributed to the owner's single occurrence without a trace. Two independently reproducible risks were fixed: first server hydration could discard a send created after the cached preview, and a known older identical prompt/conflicting idempotency key could be mistaken for a new prompt's echo. Hydration now identifies cached rows explicitly and preserves newer local messages; a late cache read cannot overwrite them either. Tests exercise delayed hydration on both OpenClaw and Hermes, repeated prompts, multiple tool calls, batched stream/completion events, stale/split/aggregate history and stable render keys. Phone acceptance remains with the owner; no simulator or live service mutation is used.
