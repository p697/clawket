# Native work inspection

`ClawketUI` presents a host-owned work record, without importing Runtime, parsing tool JSON or executing commands. The optional `ConversationPresentation.work` defaults to nil; a missing or unsupported inspection capability hides the dock. The existing message-level `WorkPresentation` remains source compatible while the host maps current and historical tool records to the richer inspector.

The 44-point minimum dock sits above the existing composer. It opens the system sheet and a native navigation list; a step opens its full detail. Accessibility text sizes may increase the height. The composer, expanded editor and transcript retain their identity. Opening or updating work does not change focus, resign the text view, increment the transcript scroll request or change the selected conversation. The system owns keyboard presentation around its sheet. Lists use stable IDs with no forced scrolling or arrival animation. Physical keyboard/IME, reading-anchor, VoiceOver and adaptive layout acceptance remain device checks.

## Host contract

- `WorkDockPresentation` supplies the current localized or backend-authored title/detail, explicit status, producer clocks, inspection availability and all authorized records. Its ID is a stable host-wide presentation identity within the concrete conversation; replace it when a different record scope must invalidate an open inspector.
- `WorkRunPresentation` is one exact run/turn/input grouping. Preserve `RuntimeWorkUpdate.runID`, `turnID`, `inputMessageID` and `inputMessageKey` in `WorkLineage`; never infer missing attribution from timestamps, adjacent messages or prose. A reused wire run with a different turn/input gets a distinct record ID. Supply a semantic title and an authorized input preview; absent attribution is labeled “Unattributed work”. Opaque IDs are not displayed, copied into product text or used for diagnostics.
- `WorkStepPresentation` preserves the canonical item/render identity, kind, explicit status and clocks, plus bounded detail content. Run and step `order` values are host-owned canonical sequence numbers. The UI sorts them newest first, preserving original order on ties; missing/skewed producer clocks do not change ownership or order.
- Map explicit running/success/error to running/succeeded/failed. Missing or unknown states remain unknown. Waiting/stopped require actual host evidence. Neither output text, a finished clock, a later tool nor a Stop ACK proves completion. Producer started/finished timestamps are localized as dates; only an explicitly supplied nonnegative duration is shown. No recovered timer starts from the current time.
- `WorkContentSection` contains already authorized, bounded verbatim text for input, output, command, error or other detail. Inspection and text selection are separate explicit permissions and default closed. Unsupported sections are hidden; temporarily unavailable sections show the host's explanation without their retained text. Text is literal, including whitespace and code fences; no Markdown interpretation, URL opening or shell action. `isComplete = false` discloses partial content instead of presenting a resource cap as the full output. Preserve the full authorized text when available.
- Record, step and section IDs must be unique and nonempty within their parent. Corrupted duplicate IDs are all excluded; exact step lookup rejects ambiguity rather than selecting a different execution.

The dock emits `workInspectorOpened(conversationID, workID:)`; entering an authorized step emits `workStepOpened(conversationID, workID:, recordID:, stepID:)` once per detail view lifetime. These are read intents only. The host revalidates the concrete conversation, current work identity, permissions and any async generation before loading or marking read. Dismissal has no task effect. A replaced/removed/unauthorized record makes an open detail unavailable; the navigation destination stays mounted so it cannot silently retarget to replacement content.

The app host currently handles the new intent cases as explicitly unsupported and supplies no default work data. Real Runtime aggregation, bounded storage, permission mapping and device acceptance are separate host work; there are no shipping fixtures.

## Verification boundary

`WorkPresentationTests.swift` exercises fail-closed defaults, canonical ordering with conflicting clocks, distinct lineages sharing a run ID, ambiguous record/step/content identities, permission revocation, clocks/output that do not establish success and work updates that preserve the existing draft. The actual iOS-only SwiftUI sources are compiled separately from the macOS package tests. CI also builds the real app and checks every compiled string resource. Source and build evidence do not claim a real backend work flow or device interaction acceptance.
