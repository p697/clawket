# Native work inspection

`ClawketUI` presents a host-owned work record, without importing Runtime, parsing tool JSON or executing commands. The optional `ConversationPresentation.work` defaults to nil; a missing or unsupported inspection capability hides the inspection entry. The existing message-level `WorkPresentation` remains source compatible while the host maps current and historical tool records to the richer inspector.

With at least 500 points of actual outer conversation height, the 44-point minimum dock sits above the existing composer. Below that height, or while editing expanded, the same entry becomes an independent 44-point native navigation control beside the conversation menu. It retains the explicit status glyph, full accessible title/detail/status/duration and inspection explanation, including disabled inspection. This uses available window height, not keyboard focus, device names or a guess that work is idle; all six statuses follow the same rule and exactly one inspection entry remains. It opens the same system sheet and native navigation list; a step opens its full detail. Accessibility text sizes may increase the body dock height. The composer, expanded editor and transcript retain their identity. Opening or updating work does not change focus, resign the text view, increment the transcript scroll request or change the selected conversation. The system owns keyboard presentation around its sheet. Lists use stable IDs with no forced scrolling or arrival animation. Physical keyboard/IME, reading-anchor, VoiceOver and adaptive layout acceptance remain device checks.

## Host contract

The entry exposes one explicitly labeled accessibility button. Its status glyph is decorative; the outer title/value retains the real status, detail, duration and inspection explanation. This prevents the toolbar's symbol from supplying a second, unrelated “selected” action. Runtime accessibility and activation still require actual device or WebDriver verification.

- `WorkDockPresentation` supplies the current localized or backend-authored title/detail, explicit status, producer clocks, inspection availability and all authorized records. Its ID is a stable host-wide presentation identity within the concrete conversation; replace it when a different record scope must invalidate an open inspector.
- `WorkRunPresentation` is one exact run/turn/input grouping. Preserve `RuntimeWorkUpdate.runID`, `turnID`, `inputMessageID` and `inputMessageKey` in `WorkLineage`; never infer missing attribution from timestamps, adjacent messages or prose. A reused wire run with a different turn/input gets a distinct record ID. Supply a semantic title and an authorized input preview; absent attribution is labeled “Unattributed work”. Opaque IDs are not displayed, copied into product text or used for diagnostics.
- `WorkStepPresentation` preserves the canonical item/render identity, kind, explicit status and clocks, plus bounded detail content. Run and step `order` values are host-owned canonical sequence numbers. The UI sorts them newest first, preserving original order on ties; missing/skewed producer clocks do not change ownership or order.
- Map explicit running/success/error to running/succeeded/failed. Missing or unknown states remain unknown. Waiting/stopped require actual host evidence. Neither output text, a finished clock, a later tool nor a Stop ACK proves completion. Producer started/finished timestamps are localized as dates; only an explicitly supplied nonnegative duration is shown. No recovered timer starts from the current time.
- `WorkContentSection` contains already authorized, bounded verbatim text for input, output, command, error or other detail. Inspection and text selection are separate explicit permissions and default closed. Unsupported sections are hidden; temporarily unavailable sections show the host's explanation without their retained text. Text is literal, including whitespace and code fences; no Markdown interpretation, URL opening or shell action. `isComplete = false` discloses partial content instead of presenting a resource cap as the full output. Preserve the full authorized text when available.
- Record, step and section IDs must be unique and nonempty within their parent. Corrupted duplicate IDs are all excluded; exact step lookup rejects ambiguity rather than selecting a different execution.

Both entry positions emit `workInspectorOpened(conversationID, workID:)`; entering an authorized step emits `workStepOpened(conversationID, workID:, recordID:, stepID:)` once per detail view lifetime. These are read intents only. The host revalidates the concrete conversation, current work identity, permissions and any async generation before loading or marking read. Dismissal has no task effect. A replaced/removed/unauthorized record makes an open detail unavailable; the navigation destination stays mounted so it cannot silently retarget to replacement content.

The actual app now binds Runtime work to `NativeTaskJournal`, supplies the local authorized inspector, and validates both read intents against the exact conversation/dock/record/step identity. These reads issue no command or RPC. See [WORK-JOURNAL.md](WORK-JOURNAL.md) for aggregation, bounds, cold recovery and remaining reconciliation/device acceptance. There are no shipping fixtures.

## Verification boundary

`WorkPresentationTests.swift` exercises fail-closed defaults, canonical ordering with conflicting clocks, distinct lineages sharing a run ID, ambiguous record/step/content identities, permission revocation, clocks/output that do not establish success and work updates that preserve the existing draft. Two actual-app `NativeReadingLayoutTests` methods additionally host the production conversation in a real `NavigationStack`. They check the same native editor/transcript, exact draft bytes/selection/reading anchor across constrained/roomy heights and all six work-state updates, plus bounded native title/editor geometry at narrow and accessibility sizes across inspection-availability changes. Public in-process accessibility/automation discovery returned no semantic nodes in the actual test windows, so these fixtures do not prove Work entry uniqueness, status accessibility, 44-point targets or Back/Work/More separation. Those checks, actual taps, expanded-editor gestures and VoiceOver remain explicit WebDriver/device acceptance; execution evidence belongs to the exact CI head. The actual iOS-only SwiftUI sources are compiled separately from the macOS package tests. CI also builds the real app and checks every compiled string resource. Source and build evidence do not claim a real backend work flow or device interaction acceptance.
