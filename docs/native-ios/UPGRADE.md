# Expo installation preservation

`ClawketUpgrade` is a read-only source reader and transactional staging boundary for a same-bundle native replacement. It does not activate connections, change purchase identity, delete legacy data or start pairing. A separate QA bundle uses synthetic fixtures; it cannot construct a production reader for the installed store bundle. Actual signed same-bundle upgrade acceptance remains an owner/release checkpoint before the native target becomes the default.

## Host integration

Construct `ExpoLegacySource.currentApplication(expectedBundleIdentifier:)` only for the current application. Supply three dedicated stores to `UpgradeImporter`: a Keychain-backed secret store, a file-backed plain store, and a `DocumentStore` for the manifest configured with `UpgradeLimits.manifestBytes` (8 MiB). Every staged chunk is at most 128 KiB. Keep these namespaces separate from normal writable native state and preserve them until every consumer has adopted its data.

Call `importIfNeeded()` before creating a new device identity, registry, purchase SDK identity or defaults. Only a successful result permits activation. A source/validation/storage failure must show recovery and keep the previous installation intact; it must never fall through to a fresh empty account. An existing verified receipt returns committed data without rereading old files. Concurrent import attempts fail with `busy`; cancellation before commit publishes no receipt. Once verified commit begins, a successful commit remains valid even if cancellation arrives afterward.

The result exposes the original device key pair and creation time, current or rollback connection registry, original connection IDs/timestamps, service environment/debug supplements and RevenueCat current/legacy app-user IDs. Map these validated values into native domain models without minting replacements. `deviceToken(connectionID:deviceID:role:)` resolves only imported connections with the preserved identity; it reproduces Mobile's exact endpoint/Relay-scope hash, role suffix and operator-only legacy fallback. New scoped tokens remain the native credential provider's responsibility.

`preservedValue(LegacyValueID)` returns verified original bytes for preferences, drafts, chat caches, read watermarks, favorites, archives, document state, entitlement state and other app-owned values. Their schemas remain owned by their native consumers. This staging module does not claim those consumers are implemented. Keep the source and receipt available until each consumer's explicit migration has succeeded.

`readResource(relativePath:offset:maximumBytes:)` reads copied voice/share content in bounded ranges. Resource paths remain sandbox-relative. Do not pass old absolute URLs into native file APIs. Copy consumers may stream ranges into their own protected destination; metadata files and checkpoint files are preserved alongside audio/attachments. A 19.2 MB unsent recording is never forced into an 8 MiB value-store entry. Completed launch does not depend on the original file remaining after normal later consumption.

## Compatibility and failure behavior

The reader uses Expo's `app:no-auth`, `app:auth`, then `app` Keychain service precedence, with UTF-8 `Data` account and generic attributes. It never expands access groups or prompts for authentication. AsyncStorage uses its current application-support path, inline strings and null-to-MD5 filenames; two older document-directory layouts remain readable without moving them. The current store wins; ambiguous legacy candidates, corrupt manifests, missing files and unsafe symlink paths fail closed.

The current registry wins when valid; its saved rollback is used when necessary. Legacy config/profile/single-connection formats remain recoverable. All six current backend identities and five transport kinds remain separate from service environment. A missing install marker follows Mobile's fresh/upgraded rules, with recognized owned files also preserving pre-marker unsent content. Fresh installation retains only the existing device identity, one-time entitlement/grace state, install marker and purchase SDK defaults; it does not resurrect Keychain-only connections, tokens or preferences.

Unknown app-owned logical values retain their exact bytes. Import limits are explicit: 16,384 values, 4,096-byte keys, 1 MiB per secure value, 64 MiB per plain value and 256 MiB logical values total; 2,048 resources, 32 MiB each and 512 MiB total. An oversized installation is a recoverable import failure, never truncated or silently evicted. Receipt metadata contains references and hashes; secret bytes stay exclusively in the supplied secret store. Writes are read back byte-for-byte and copied resources are hashed before the final verified manifest is published. Failed staging can leave unreachable chunks for a future explicit cleanup policy, while original data stays unchanged.

## Verification

Strict Swift 6 compilation and three selected test files passed serially with two build jobs: `UpgradeValidationTests` (6), `ExpoLegacySourceTests` (6) and `UpgradeImporterTests` (11). These exercise synthetic Keychain query attributes without opening Keychain, actual inline/MD5 files and old paths, a real 19,200,000-byte PCM file, six-backend registry/rollback, identity/scoped tokens, purchase/grace preservation, large values, cancellation, overlapping attempts, failed writes/read-back, copied-resource corruption, and restart after original-resource deletion. No store app or production credential was read. Same-bundle entitlement/access-group continuity and end-to-end native consumer acceptance are separate from these module tests.
