# Codex / Claude Code 连接体验实测（2026-11-21）

负责人要求：以远程使用多台电脑上的 Codex 和 Claude Code 为目标，实测连接与对话体验，小问题直接修，大改动先出方案。本页是这一轮的证据、已做的修复和等负责人决定的事项。

## 环境

- 电脑：Codex Desktop 26.1117.41037（应用包 `ChatGPT.app`，自带 codex 0.171.0-alpha.13，当天 12:02 自动更新），Homebrew codex 0.167.0，Claude Code 2.1.319，公开 Bridge 3.1.18（launchd 管理的快照）。出站流量经 Clash Verge。
- 手机：「Clawket RN Connection QA」模拟器（iPhone 17 Pro，iOS 27.2），当前 main 的 JS 换进 11-08 的 Release 模拟器包；Production 配对。只在 Chats 项目的测试对话里发消息，没有碰负责人的对话。
- 计时方法：`simctl` 每约 0.4 秒截一张图，按画面变化读时间；误差约 ±0.4 秒。模拟器与电脑共用网络，测不到手机蜂窝网络、Wi-Fi 切换和手机侧代理。

## 连上之后是顺的

| 场景 | 结果 |
|---|---|
| 冷启动到首页 | 约 4.3 秒（其中启动图约 3 秒） |
| 首页出现到 Codex 连上（绿点） | 再 2–3 秒 |
| 已连接时点开 Codex 进入上次对话 | 约 0.8 秒，历史直接可见 |
| 新建对话（选 Chats 项目） | 约 1.2–2.7 秒 |
| 发消息到出现第一段回复 | 约 2 秒；5 条命令 + 长回复全程正常，结束后有「运行了 5 个命令 · 26 秒」 |
| 切后台 45 秒再回来 | 无可见变化 |
| 进程冻结 150 秒（模拟 iOS 挂起）再回前台 | 头部一直是「在线」，无可见重连 |

## 故障态才是体验差的来源

### 1. Bridge 的 Codex 子进程凭据失效，手机永远连不上（已修）

- 现象：点开 Codex 后「正在连接」20 多秒，随后一直是「离线 · 正在重连」。
- 原因：Bridge 握手用的 `health` 调原生 `account/read`。Bridge 自己的 App Server 子进程已运行 13 天，电脑上的登录在当天 09:32 更新后，这个旧进程从 10:04:58 起每次刷新都被拒（原生日志：登录已变更，需要重新登录），`account/read` 返回 -32603，`health` 整个失败。新启动的进程读同一份登录是正常的（两个版本各起一个独立 App Server 实测）。
- 影响：从 10:05 到 15:08 手动 `clawket codex restart` 为止，这台电脑的 Codex 完全连不上。`clawket codex status` / `doctor` 只说「health could not be verified」，Bridge 日志里没有这次失败的任何记录。
- 修复：见「已做的修复」。

### 2. 新版 Codex Desktop 下，已有对话发不出消息（待决定）

- 现象：Bridge 重启后，在 11-08 由手机创建的测试对话里发消息，提示「发送失败，请确认对话内容后再重试」。
- 原因有两层：
  - Codex Desktop 26.1117 的应用包里已经没有 Bridge 使用的桌面 IPC 协议（`thread-stream-following-changed`、`no-client-found`、`initialize {clientType}` 等字符串全部不存在），`~/.codex/ipc/ipc.sock` 是前一天遗留的文件，连接被拒。Bridge 每 2 秒重试一次，当天 3 小时内记了 5,100 多条 `connection_lost`。
  - 没有桌面 IPC 时，Bridge 只允许在 `0.153.3` 和 `0.158.0-alpha.2.1` 两个原生版本上对自己创建的对话做原子恢复；从桌面导入的对话一律要求桌面明确答复无人占用。本机之前自带的 0.167.0 和现在的 0.171.0-alpha.13 都不在名单里。
- 结果：在当前 Desktop 上，手机只能给「本次 Bridge 进程里新建的对话」发消息；Bridge 一重启（包括更新），所有已有对话都只能看、不能续。提示文案也不对：详情里写的是「打开电脑上的 Codex Desktop」，而 Desktop 开着。
- 本轮实测到的原生事实（0.171.0-alpha.13，两个独立 App Server、一条一次性对话）：
  - 第二个进程 `thread/resume` 同一对话，返回 `thread <id> already has an active writer`，即跨进程的原子写入锁仍在，报错文本与 Bridge 现有映射一致。
  - `thread/unsubscribe` 之后 1.5 秒内锁没有释放；持有进程退出后，另一个进程可以恢复。
  - 没有发过消息的空对话没有 rollout，无法用来验证锁，所以这项验证做不成不花模型调用的自检。
- 新版本同时提供了官方的多客户端入口（只看了帮助和协议定义，没有启用）：`codex app-server daemon` / `proxy`（本机常驻 App Server 与控制套接字）、`codex queue --thread --message`、协议方法 `thread/queue/add|list|start`、`thread/loaded/list`、`project/list`、`remoteControl/*`。

### 3. 隧道每小时断一次（环境因素，产品要扛得住）

- Codex 与 Claude Code 两条 Bridge 隧道，11-07 以来每天各断 25–40 次，11-13、11-17 各 120–160 次。恢复耗时中位数约 1 秒、P90 约 5–6 秒；超过 60 秒的各 34–35 次，最长一次约 4.6 小时。
- 心跳兜底超时集中在每小时的 :59:44–:59:57（另有 :29–:30），与进程启动时间无关；表现是对端不再回应而不是收到关闭帧，符合代理链路定时重置。产品代码没有整点任务。
- Bridge 掉线或被新连接替换时，Relay 立即以 4011 关闭这台电脑的全部手机连接；Bridge 与 Relay 都不缓冲事件，手机靠重新握手和重拉历史补齐。15:59 的那一次在模拟器上抓到了（停在一条空闲的 Claude Code 对话里）：Bridge 15:59:39 发现对端不回应，15:59:43 断开，15:59:45 重新就绪；手机头部 15:59:47 从「在线」变成「正在重连…」，15:59:51 恢复，持续约 4 秒，对话内容没有变化。正在流式回复时遇到这次断线的表现没有测。

### 4. 手机端重连链路里读代码确认的拖慢点

- 新建 adapter（冷启动、切换连接、手动重连）时「连上过」的标记归零，握手遇到 `BRIDGE_UNAVAILABLE` 第一次重试就等 30 秒（已修）。
- 从首页点 Agent 进入对话是串行的：握手 → 会话目录全量同步 → 写缓存 → 才跳转 → 才拉历史。
- 冷启动连接期间，聊天页已恢复的缓存消息被加载画面挡住，直到 ready。
- 会话目录的增量基线只在内存里，冷启动、切换、手动重连都重新拉全量（本机 Codex 1,256 条、12 页，本地约 0.3 秒；经隧道未测）。
- 回前台和发送前的探活分别是 2 秒和 1.5 秒超时，超时就拆掉连接重建。
- ready 时 `agents.list` 发两次；换 adapter 时模型芯片先显示占位再出模型名（实测可见一次「模型」→「GPT-6.2-…」）。

### 5. Claude Code

- Bridge 健康；`sessions.list` 216 条约 1.1 秒，每次都会执行一次 `claude agents` 并全量扫描。
- 读代码确认：在 Desktop 里打开过、没有归档的对话算被占用，手机只能「复制一份接着聊」；导入的对话每轮结束都释放进程，下一轮重新冷启动；同时最多 2 个进程。
- 模拟器实测：会话面板能列出电脑上的对话，包括正在运行的那一条（带运行标记）。从 Codex 切到 Claude Code 连接，全屏等待约 6.6 秒（握手约 2–4 秒，加载会话约 2 秒），而已连接时进聊天只要约 0.8 秒：同一时间只有当前连接保持着隧道，切换连接就是一次完整重连。
- **新建对话的第一条消息发不出去（部分已修，根因待决定）。** 在 Chats 项目新建对话后发送，20 秒后提示「发送失败」，详情是 `Claude Code request timed out`，连发三次都一样。Bridge 确实启动了 Claude 进程，但进程 30 秒内没有完成初始化就被回收。电脑屏幕上此时有一个系统弹窗：「“2.1.319”想访问“文稿”文件夹中的文件」。默认聊天目录 `~/Documents/Clawket/Chats` 在 macOS 受保护的「文稿」里，新版本的 Claude Code 可执行文件第一次读取它时，系统要在电脑前确认，进程就停在那里；人不在电脑前，这条路就一直不通。Codex 在同一目录当天可以正常执行。
- 新建对话的项目列表按名称排序，本机被二十多个 worktree 目录占满（很多已不存在、置灰），常用的 clawket、prompix 要往下翻（排序已修，见「已做的修复」第 4 条）。
- 会话预览会露出系统附带的图片说明文字（例如「[Image: original 1206x2622, displa…」）。
- 续聊实测（当晚补做）：列出的 218 条对话里 201 条可以直接续聊，只有正有进程的那一条被占用；经 Bridge 续聊能接上原对话并保留上下文。代价是导入的对话每轮都重启进程，12–18 秒才出第一个字，进程保留时约 4 秒。两个进程写同一条对话的实验（一次性测试对话）：Claude Code 没有任何跨进程保护，留着的进程看不到另一个进程写的那一轮，它的下一轮会把记录分叉，另一方那一轮在之后的恢复里丢失。所以「空闲的占用者也是占用者」必须保留。
- 同时发现：手机上删除自己新建的对话后，它的记录还在电脑上，会作为「电脑上的对话」重新出现；导入的对话如果记录已被删掉，手机上没法移除这一行。
- 没有实测「复制一份接着聊」。

### 6. 其他观察

- Codex 会话列表里大量标题为「[OpenClaw conversation info: sen…」的行：OpenClaw 借 Codex 引擎运行时在 `~/.openclaw/workspace` 等目录产生的对话，本机 workspace 一个项目就有 261 条。
- 新建对话的项目列表不是按最近使用排序（昨天用过的 prompix 排在第五）。
- 重启提示里写的是「Codex · Computer」，而保存的名字是「Codex · Lucy的Mac mini」。

## 已做的修复

1. **Bridge：凭据失效不再让握手失败，空闲时自愈。** `account/read` 被原生拒绝时，`health` 返回 `modelReady: false`，手机可以连上、看会话和历史。没有运行、待确认的启动和设置写入时，Bridge 替换自己的 App Server 子进程一次并重读账号，十分钟内最多一次；每次记录 `account_read_rejected` / `account_recycle`。超时和进程丢失这类未知结果仍让握手失败。不接管、不结束任何别的进程。
2. **Mobile：以前连上过的连接冷启动走短重试。** 协调器把名册缓存里的 `lastReadyAt` 作为 `previouslyReady` 传给 Codex / Claude Code / Pi adapter；新 adapter 遇到 `BRIDGE_UNAVAILABLE` 时按 2/4/8/8 秒重试一轮，之后回到 30/60/120 秒。从未连上过的连接不变。

3. **Claude Code 首条消息的等待与提示。** Mobile 把 Claude Code `chat.send` 的等待从 20 秒放宽到 45 秒，覆盖占用检查（8 秒）加进程初始化（30 秒），不再先于 Bridge 的结论报「超时」。Bridge 在 macOS 的文稿、桌面、下载目录里初始化失败时，提示改为「Claude Code 没有在这个文件夹启动；如果电脑上正在询问是否允许访问该文件夹，请在电脑上允许后再发」（英文原文，未做 19 语言）。这只让失败说得清楚，弹窗本身仍要有人在电脑前点。

4. **项目列表最近优先。** Mobile 在新建对话的项目选择里，把最近有对话的项目排在前面，已不存在的目录排到最后，其余保持 Bridge 的顺序；Codex 与 Claude Code 共用。worktree 目录本身仍在列表里。

5. **Claude Code 续聊提速与列表清理（负责人 2026-11-21「按建议改」）。** 导入的对话在一轮结束后把进程保留 2 分钟，下一条消息复用它；复用前确认占用名单可读、这条对话没有第二个进程、记录的修改时间和大小与本轮结束时一致，任一不满足就关掉进程、按原来的占用检查重新来。手机上删除或重置的对话不再作为电脑上的对话回到列表。文件夹或记录已经不在的导入对话可以从手机上移除。实测数字见 `claude-code.md` 与 PROGRESS。

6. **Claude Code 回复写完就结束（2026-11-22，负责人授权自行推进）。** Claude Code 在每轮回复之后还要再调用一次模型给这一轮写摘要，写完才报告结束；这期间手机一直显示运行中、不能发下一条。实测最后一个字到结束：网络好时 4–5 秒，当晚网络差时 10–28 秒。现在 Bridge 在回复的最后一条消息以正常结束收尾时就告诉手机这一轮结束，原生的收尾在后台完成；收尾期间发来的下一条消息照常接受，由原生排队执行。改后实测间隔约 10 毫秒。预热新对话进程的想法实测没有收益（进程启动只要 0.2–0.6 秒，慢的是进程里的第一次请求），没有做。

7. **Claude Code 回复中途断线后文字缺一段（2026-11-22）。** 读代码确认并用手机端测试复现：Claude Code 的回复按增量发送，Bridge 和 Relay 都不缓冲；手机在回复中途重连后，把后续增量接在断线前的文字后面，中间丢的那段一直缺到整轮结束（Codex 每次发整段，没有这个问题）。现在 Bridge 约每 1.5 秒用整段文字替换一次增量，手机端原有逻辑会直接用整段覆盖，缺口最多持续 1.5 秒。

8. **没发出去的消息不再在重开 App 后消失（2026-11-22）。** 读代码确认两处：发送结果未知的消息在缓存里带着标记，但冷启动后第一次读电脑历史会把缓存恢复的行全部替换掉，它就没了；发送途中被关掉 App 的消息，缓存里连标记都没有。现在发送还没得到答复的消息以「未确认」存进缓存（屏幕上仍是正常的发送中）；冷启动时缓存里最新 20 条未确认消息先放进内存里的恢复区，历史替换后仍显示为未确认，直到电脑历史里出现同一条消息的确切标识才消失。不自动重发。

以上都要随后续授权的 Bridge 发布和 App 更新才到达用户。

## 待决定

1. **（2026-11-21 已决定并实现，见 `codex.md`「Continuation without a Desktop broker」）原子恢复的版本策略。** 现在是逐版本登记，Desktop 每周自动更新，名单永远落后。建议改为「0.158.0 及以上都依赖原生写入锁」，并保留现有的空闲历史检查和「already has an active writer」拒绝映射；依据是 0.171.0-alpha.13 上的实测。这会改动根 `AGENTS.md` 里「只在明确验证过的原生版本上」这条规则，所以需要负责人点头。
2. **（已决定并实现：实测发现取消订阅约 60 秒后原生会自行释放写入锁，所以没有采用「每轮临时进程」，改为 Bridge 自己续聊、空闲后放手）新版 Desktop 下续聊桌面对话。** 桌面 IPC 没了，三条路：
   - 临时写入者：对导入的对话，每轮用一个只为这一轮存在的 App Server 进程恢复、执行、退出，靠原生写入锁保证不与桌面同时写；桌面开着该对话时明确提示「正在电脑上打开」。与 Claude Code 现有做法一致。建议走这条，先在真实 Desktop 窗口验证「手机续聊后电脑重开正常」。
   - 官方消息队列：用 `thread/queue/add` 把消息交给持有对话的进程执行，适合「桌面正开着这条对话」的情况；手机拿不到流式过程，只能轮询历史。可作为第二步补充。
   - 暂不支持，只修文案。
3. **（2026-11-21 已决定并实现：「全部项目」列表不再混入 `.openclaw` 工作区里的对话，选中该项目或搜索时照常显示）OpenClaw 借 Codex 引擎产生的对话**是否从 Codex 列表里默认收起。
4. **（2026-11-21 已决定并实现：新配对用 `~/Clawket/Chats`，已有配对保持原目录）默认聊天目录的位置。** 新配对默认把对话放在 `~/Documents/Clawket/Chats`，这是系统会弹窗确认的目录。建议新配对改到不受保护的位置（例如 `~/Clawket/Chats`），已有配对保持原目录不动；是否提供一条把旧目录迁过去的命令另议。
5. **（2026-11-21 已实现前者：先显示保存的对话、后台再连；同时保持多条隧道未做）切换连接的 6–7 秒全屏等待。** 两个方向：先显示该连接缓存的上次对话、后台再连（改动集中在入口页和聊天页的切换判定）；或者让最近用过的两三个连接同时保持隧道（改动在连接协调器，涉及电量和 Relay 连接数）。建议先做前者。
6. **握手被拒时的手机提示**：旧 Bridge 仍会遇到第 1 条故障，是否加一条「电脑上的 Codex 需要重启 Clawket」的可读提示（19 种语言）。

## 局限

- 凭据失效的现场没有再造；自愈逻辑由单元测试覆盖，「新进程读得到新登录」是实测。
- 没有操作 Codex Desktop 窗口，桌面侧的占用行为只来自协议与两个独立 App Server 的实验。
- 每小时断线的原因是推断，没有在不经代理的网络上对照。
- 真机、蜂窝网络、多台电脑同时在线都没有测。
