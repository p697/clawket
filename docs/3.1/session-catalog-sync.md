# Bounded session catalog synchronization

Codex, Claude Code and Pi advertise `sessionCatalogSync: 1` in authenticated health. New clients use `sessions.sync`; older clients keep `sessions.list` and its unchanged array response. OpenClaw and Hermes do not use this endpoint.

The first successful read returns a frozen `full` page with a boot-scoped epoch, random revision, offset, total row count and next offset. Every page is at most 64 KiB of serialized UTF-8 JSON, including its payload envelope. A page request references that exact epoch/revision/offset and never rescans native history. The service retains two snapshots, each limited to 10,000 rows and 8 MiB. Unknown initial bases receive a first full page; evicted continuation pages return `expired`. A consumer may restart that read once and must publish only a complete validated array.

An exact current base returns `unchanged`. A retained older base may receive a small `delta` with upserts, removed keys and the complete final ordering; oversized deltas use paged full instead. Snapshots and revisions reflect only successful complete discovery. Simultaneous refreshes share one read, while independent clients may use different retained bases. Successful management acknowledgements invalidate pending refreshes without erasing a complete baseline or its frozen pages. An obsolete read may join one fresh scan; repeated invalidation returns a fixed retryable read error instead of publishing stale rows or waiting indefinitely. Snapshot objects cannot be mutated by returned pages. Catalog data remains in memory; no transcripts or credentials are added to storage.

Claude sync rejects failed, malformed, duplicate or safety-truncated SDK discovery while its legacy listing remains tolerant. Codex sync rejects incomplete catalog membership; optional preview failures retain existing preview behavior. Both preserve known native history lookups during partial scans and admit only bounded, positively validated entries in the same scope. Only complete scans or explicit confirmed management operations may remove those lookups. Retained metadata does not authorize continuation or replace fresh ownership/project checks; incomplete Codex discovery cannot reconcile names/archive state or infer missing active threads, or undo a confirmed reset/delete. Pi completely enumerates filenames, reads its existing recent 200-file window and retains previously known rows for still-present files that are temporarily unreadable or have moved outside that window. Confirmed file absence may remove a row; enumeration failure cannot. Unsupported new Pi files retain the existing skip behavior.

This removes repeated full catalog frames during idle maintenance and bounds the first transfer into small pages. It does not claim to speed up native discovery itself, change native ownership, guarantee atomicity across concurrent native filesystem edits, or solve every large history/image transfer. A single descriptor above the page budget or a catalog above the overall cap fails explicitly rather than silently truncating or deleting conversations.

Claude SDK's optional absent `cwd` is an eligibility exclusion, not a malformed scan. Unscoped rows never borrow a default/cached project and do not block syncing other conversations. Complete discovery may withdraw their native lookup; failed reads, malformed present fields, duplicates and scan limits still preserve the previous snapshot. Pagination progress counts fresh SDK identities before project filtering. See [Claude discovery](claude-code.md#ownership-and-discovery).

## Codex connection latency (2026-10-02)

Codex additionally advertises `sessionCatalogPageIndex: 1`. A newly negotiated client may add `pageIndex: true` to its initial/base request. Only a full first page adds optional `pageOffsets`, a strictly increasing list of exact continuation offsets for that immutable epoch/revision. The index is at most 512 offsets and stays within the existing 64 KiB page budget. A near-limit first row may omit the optional index. A single-page catalog remains one page, including when the empty index would exceed its budget. Continuation requests remain unchanged; unknown/old peers and all unindexed reads use the original serial path. Claude Code and Pi do not advertise this extension; OpenClaw/Hermes do not use catalog sync.

Mobile reads those independent continuations in groups of at most three, waits for each group to settle, validates exact contiguous offsets, epoch/revision, total, unique descriptors/order and byte limits, then publishes only the complete list. Out-of-order network completion is harmless. An expired group discards every partial row and restarts once; failure, retirement or management supersession cannot replace the last complete baseline. No writes, new native owner, cloud storage or larger frame is introduced.

A controlled test using the real Bridge pager and Mobile consumer, 1,023 generated descriptors and 300 ms per RPC took 3,000 ms for ten serial exchanges and 1,200 ms for the same ten exchanges in a three-page window. This isolates network round trips; it is not phone, production or inference performance evidence. The existing standalone loopback diagnostic on this Mac measured health 42 ms and 1,023 valid rows across ten pages in 629 ms on October 2 at 00:17 UTC. That local result does not include the phone/Relay path.

Conversation entry shows `Loading sessions` immediately after the real handshake becomes ready, including while `activate` still awaits its first catalog. Cold activation already forces a complete list: the picker reuses that live scoped result instead of requesting it again. Failed/cache-only activation keeps the fallback refresh, and revisiting an already-ready scope keeps its normal refresh. Known last-session, archive, permission and adapter-identity checks remain in force.

The Codex entry slow hint appears only after 12 seconds without progress in the current connection/catalog stage. Actual readiness advances the stage and starts its clock once; rerenders/callback changes do not postpone it. Other backend entries and generic loaders retain six seconds. This changes warning presentation, not connection/RPC deadlines or the stability SLO. The optimization needs compatible App and Bridge updates; the stage/hint and duplicate-read fixes need an App update. Source verification does not publish either.
